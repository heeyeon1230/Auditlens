# AuditLens 요구사항 및 설계안 (1·2단계)

작성일: 2026-10-03 · 작성: 김희연 (Claude와 협업)

> 원본은 Claude Docs 문서이며, 이 파일은 저장소 보관용 사본입니다.

AuditLens 첫 버전은 **Python + Streamlit 로컬 앱**으로, 분개장 1개 파일을 올리면 검증 → 분석 → 8개 이하의 설명 가능한 규칙으로 검토 후보를 표시하고, 각 후보에 사유와 근거를 붙여 내려받게 하는 범위로 제안합니다. 이 문서는 1단계(요구사항)와 2단계(설계)의 산출물이며, 코드는 아직 작성하지 않았습니다.

문서 전체에 적용되는 전제는 세 가지입니다.

- **가상 데이터만 사용**합니다. 샘플 분개장은 프로그램이 규칙에 따라 생성하며, 실제 회사 자료는 저장소에 넣지 않습니다.
- **탐지는 결론이 아닙니다.** 화면과 파일 어디에서도 "부정", "오류"라는 표현 대신 "검토 후보"와 "탐지 사유"를 씁니다.
- **기준 근거는 범위를 밝혀 인용합니다.** 감사기준서 240(재무제표감사에서 부정에 관한 감사인의 책임)과 330(평가된 위험에 대한 감사인의 대응)은 분개 테스트의 필요성과 일반적 고려 특성을 다루지만, 구체적 임계값(예: 표준편차 몇 배)을 정하지는 않습니다. 따라서 이 문서의 수치 기준은 모두 **조정 가능한 기본값**이며 기준서가 정한 값이 아닙니다. 기준서 조문 번호와 문구는 구현 전에 원문으로 다시 확인할 예정입니다.

## 1. 핵심 사용자와 해결하려는 문제

핵심 사용자는 분개 테스트 대상을 고르는 **현장 감사인** (스태프\~시니어)이고, 해결할 문제는 "수만 건의 분개 중 왜 이 건을 봐야 하는지"를 빠르고 일관되게, 근거와 함께 제시하는 것입니다.

| 사용자 | 하는 일 | 지금의 불편 | AuditLens가 주는 것 |
| --- | --- | --- | --- |
| 현장 감사인 (주 사용자) | 분개장 수령, 모집단 완전성 확인, 테스트 대상 선정 | 엑셀 필터·피벗을 매번 수작업, 선정 사유 기록이 사람마다 다름 | 같은 기준을 반복 적용, 건별 탐지 사유가 붙은 후보 목록 |
| 검토자 (매니저·파트너) | 대상 선정의 적절성 검토 | 어떤 기준으로 뽑았는지 추적이 어려움 | 적용한 기준값과 규칙 설명이 함께 내보내지는 결과 파일 |
| 채용 담당자 (포트폴리오 독자) | 지원자의 역량 판단 | 회계 지식과 데이터 역량을 동시에 확인하기 어려움 | 샘플 데이터로 바로 체험하는 시연 화면 |

해결하지 않는 문제도 분명히 합니다. AuditLens는 부정·오류 여부를 판단하지 않고, 모집단 완전성(시산표 대사)을 대신하지 않으며, 표본 추출의 통계적 대표성을 보장하지 않습니다.

## 2. MVP 기능과 후순위 기능

요청하신 10개 기능은 모두 MVP에 넣되, 탐지 규칙은 6절의 8개 중 **설명이 쉬운 6개를 먼저** 구현하고 나머지 2개는 후순위로 미룹니다.

### MVP (3단계에서 구현)

| 번호 | 기능 | MVP에서의 범위 |
| --- | --- | --- |
| F1 | 파일 업로드 | CSV(UTF-8, CP949 자동 시도), Excel(.xlsx 첫 시트 또는 선택 시트). 1회 1파일, 약 20만 행 이하 |
| F2 | 열 매핑·검증 | 파일의 열 이름을 표준 열에 연결하는 화면, 자료형·결측치·차대 균형 검사 (5절) |
| F3 | 계정·기간별 분석 | 계정과목별 월별 금액·건수 표와 막대그래프 |
| F4 | 이상 징후 탐지 | 규칙 R1\~R6 (6절) |
| F5 | 탐지 사유·근거 | 건별로 "어떤 규칙 / 기준값 / 실제값 / 비교 대상" 문장 표시 |
| F6 | 전체 / 검토 후보 구분 조회 | 탭 두 개, 규칙·계정·기간 필터 |
| F7 | 결과 다운로드 | CSV와 Excel. Excel에는 검토 후보 시트 + 적용 기준 시트 포함 |
| F8 | 샘플 데이터 체험 | 버튼 하나로 가상 회사 1년치 분개장 불러오기 (의도적으로 심은 이상 건 포함) |
| F9 | 탐지 기준 조정 | 사이드바에서 규칙 켜기/끄기와 임계값 변경, 기본값으로 되돌리기 |
| F10 | 한계·오탐 안내 | 전용 화면 + 규칙별 한계를 결과 화면에도 표시 |

### 후순위 (MVP 이후 검토)

- 규칙 R7 평소와 다른 계정과목 조합, R8 라운드 금액·승인 한도 직하 금액 (6절에 설계만 수록)
- 검토 후보별 감사인 메모·검토 상태 기록 (저장소가 필요해져 구조가 복잡해짐)
- 시산표·전기 분개장 동시 업로드와 대사
- 여러 규칙 결과를 합친 종합 점수 (가중치 근거를 설명하기 어려워 우선 제외)
- 머신러닝 기반 탐지(Isolation Forest 등), 생성형 AI 설명문
- 웹 배포(Streamlit Community Cloud), 로그인, 다중 사용자
- PDF 보고서 출력

## 3. 권장 기술 구성과 선택 이유

Python 3.11 + Streamlit + pandas 세 가지가 중심이고, 데이터베이스·로그인·서버는 두지 않습니다. 모든 계산은 메모리 안에서 끝나고 업로드 파일은 저장하지 않습니다.

| 구성 요소 | 선택 | 이유 | 검토했지만 제외한 것 |
| --- | --- | --- | --- |
| 언어 | Python 3.11 | 데이터 분석 자료와 채용 수요가 가장 많음 | — |
| 화면 | Streamlit | HTML·JavaScript 없이 파이썬만으로 업로드·표·슬라이더·다운로드 구현, 무료 배포 경로 있음 | Django/Flask(웹 개발 지식 필요), Dash(코드가 더 길어짐) |
| 데이터 처리 | pandas | 엑셀과 같은 표 개념, 피벗·그룹별 집계가 한 줄 | Polars(빠르나 자료가 적음) |
| Excel 읽기·쓰기 | openpyxl | .xlsx 표준 라이브러리 | .xls(구형식)은 MVP 미지원 |
| 차트 | Plotly (Streamlit 내장 호환) | 마우스를 올리면 값이 보여 설명에 유리 | matplotlib(정적 이미지) |
| 통계 | pandas 내장 함수(중앙값, 사분위수) | 별도 통계 라이브러리 없이 충분 | scikit-learn(머신러닝은 후순위) |
| 테스트 | pytest | 파이썬 표준, 규칙별 자동 테스트 | — |
| 형상관리 | Git + GitHub | 변경 이력이 남고 포트폴리오 링크로 바로 사용 | — |

### 폴더 구조 (안)

화면 코드와 계산 코드를 분리해, 규칙 하나를 고칠 때 파일 하나만 열면 되도록 합니다. 나중에 웹으로 배포할 때도 이 구조 그대로 Streamlit Community Cloud에 올릴 수 있습니다.

```text
auditlens/
├─ app.py                화면 진입점 (실행: streamlit run app.py)
├─ auditlens/
│  ├─ loader.py          파일 읽기, 열 매핑
│  ├─ validation.py      데이터 검증 (5절)
│  ├─ analysis.py        계정·기간별 집계
│  ├─ rules/             규칙 하나당 파일 하나 (r1_*.py ~ r6_*.py)
│  ├─ config.py          규칙별 기본 임계값
│  └─ sample_data.py     가상 분개장 생성기
├─ tests/                 pytest 테스트
├─ docs/                  설계서, 테스트 결과, 시연 자료
└─ requirements.txt       필요한 라이브러리 목록
```

## 4. 화면 구성 및 사용자 이용 흐름

화면은 왼쪽 메뉴의 6개 페이지로 나누고, 사용자는 위에서 아래로 한 번 내려가면 결과 파일까지 얻습니다. 검증에서 치명적 오류(필수 열 없음 등)가 나오면 다음 단계로 넘어가지 않고 업로드로 돌아갑니다.

| 페이지 | 보여주는 것 | 사용자가 하는 일 |
| --- | --- | --- |
| ① 시작 | 프로그램 목적, "탐지는 결론이 아님" 안내, 사용 순서 | 파일 업로드 또는 「샘플 데이터로 체험」 버튼 |
| ② 데이터 검증 | 열 매핑표, 자료형, 결측치 건수, 차대 불일치 전표, 오류·경고 목록 | 열 연결 확인, 경고 내용 확인 후 「분석 진행」 |
| ③ 기초 분석 | 계정과목별·월별 금액과 건수 표, 막대그래프 | 계정·기간 선택 |
| ④ 탐지 결과 | 요약(규칙별 건수), 「전체 거래」·「검토 후보」 탭, 행을 고르면 사유·근거 상세 | 사이드바에서 기준 조정, 필터, 다운로드 |
| ⑤ 탐지 기준 설명 | 규칙별 조건·이유·계산식·현재 적용값·한계 | 읽기 |
| ⑥ 분석 한계 안내 | 오탐·미탐 가능성, 데이터 전제, 기준서 근거의 범위 | 읽기 |

탐지 결과 화면의 검토 후보 한 건은 다음처럼 보입니다 (예시 값은 가상).

| 전표번호 | 일자 | 계정 | 금액(원) | 해당 규칙 | 탐지 사유 |
| --- | --- | --- | --- | --- | --- |
| JE-2025-08812 | 2025-12-31 | 매출 | 48,000,000 | R1, R3 | R1: 매출 계정 금액의 중앙값 대비 범위를 벗어남 (기준 최대 31,200,000). R3: 결산일 당일 입력, 수기 분개 |

신호등 색이나 "위험도 점수"는 처음에는 두지 않고, **해당 규칙 개수**로만 정렬합니다. 점수는 근거 없이 결론처럼 읽힐 수 있기 때문입니다.

```text
업로드 또는 샘플 → 데이터 검증 → 치명적 오류?
                                  ├─ 예: 파일을 고쳐 다시 업로드
                                  └─ 아니오 → 기초 분석 → 탐지·결과 조회 ⇄ 탐지 기준 조정
                                                              └→ 결과 다운로드 (CSV · Excel)
(기준 설명·한계 안내 페이지는 언제든 열람)
```

기준을 바꾸면 결과가 즉시 다시 계산되고, 다운로드 파일에는 그 시점의 기준값이 함께 남습니다.

## 5. 입력 데이터의 필수 열과 검증 기준

필수 열은 6개이고, 규칙에 따라 필요한 선택 열이 없으면 그 규칙만 자동으로 꺼지고 화면에 이유가 표시됩니다. 파일 열 이름이 달라도(예: "차변금액", "Debit") 열 매핑 화면에서 표준 열에 연결합니다.

데이터 형태는 **한 행 = 분개 라인 하나**(차변 또는 대변)이고, 같은 전표번호의 행들이 하나의 분개를 이룹니다. 금액은 차변·대변 두 열로 받습니다.

### 표준 열

| 표준 열 이름 | 의미 | 구분 | 자료형 | 사용하는 규칙 |
| --- | --- | --- | --- | --- |
| je\_id | 전표번호 | 필수 | 문자 | 전체, R6 |
| posting\_date | 회계처리일(전기일) | 필수 | 날짜 | 전체, R2, R3 |
| account\_code | 계정코드 | 필수 | 문자 | 전체 |
| account\_name | 계정과목명 | 필수 | 문자 | 화면 표시 |
| debit | 차변금액 | 필수 | 숫자(0 이상) | 전체 |
| credit | 대변금액 | 필수 | 숫자(0 이상) | 전체 |
| entry\_date | 입력일(시스템 등록일) | 선택 | 날짜·시간 | R3 (없으면 posting\_date로 대체하고 그 사실을 표시) |
| description | 적요 | 선택 | 문자 | R4, R6 |
| vendor | 거래처 | 선택 | 문자 | R5, R6 |
| source | 전표 원천(자동/수기) | 선택 | 문자 | R4 |
| je\_type | 전표 유형(일반/조정/결산 등) | 선택 | 문자 | R4 |
| created\_by | 입력자 | 선택 | 문자 | R4 |
| approved\_by | 승인자 | 선택 | 문자 | R4 (입력자=승인자) |

### 검증 기준

검증 결과는 **오류**(분석 중단)와 **경고**(분석은 진행, 해당 행 표시) 두 등급입니다. 프로그램은 원본 값을 임의로 고치지 않고, 바꾼 것이 있으면(예: 금액의 쉼표 제거) 검증 화면에 기록합니다.

| 번호 | 검사 항목 | 기준 | 등급 |
| --- | --- | --- | --- |
| V1 | 필수 열 존재 | 6개 필수 열이 모두 매핑됨 | 오류 |
| V2 | 빈 파일 | 데이터 행이 1개 이상 | 오류 |
| V3 | 날짜 변환 | posting\_date가 날짜로 읽히지 않는 행 | 경고 (해당 행은 분석에서 제외하고 건수 표시) |
| V4 | 금액 변환 | 쉼표·공백 제거 후에도 숫자가 아닌 행 | 경고 |
| V5 | 필수 값 결측 | je\_id, posting\_date, account\_code가 비어 있는 행 | 경고 |
| V6 | 차대 동시 기재 | 한 행에 차변과 대변이 둘 다 0이 아니거나 둘 다 0 | 경고 |
| V7 | 음수 금액 | 차변 또는 대변이 음수 (역분개 표기 방식일 수 있음) | 경고 |
| V8 | 전표별 차대 균형 | 같은 je\_id의 차변 합계와 대변 합계 차이가 1원 초과 | 경고 |
| V9 | 항목 행 중복 | 모든 열 값이 같은 행 | 경고 |
| V10 | 분석 기간 | posting\_date 최소·최대와 월 수 표시, 선택한 회계기간 밖 행 | 경고 |
| V11 | 계정코드↔계정명 일치 | 한 계정코드에 계정명이 2개 이상 | 경고 |

전체 분개장의 차변 합계와 대변 합계도 화면에 표시하지만, 시산표와의 대사(모집단 완전성)는 MVP 범위가 아닙니다.

## 6. 탐지 규칙별 설계안과 한계

제시하신 아이디어 8개를 규칙 R1\~R8로 설계했고, MVP에는 R1\~R6을 구현합니다. "금액 상위 n건" 같은 규칙은 두지 않으며, 금액은 항상 같은 계정·같은 거래처·같은 기간과 비교한 상대값으로만 씁니다.

### 공통 설계 원칙

- **규칙은 서로 독립**입니다. 한 거래가 여러 규칙에 해당하면 사유를 모두 나열하고, 해당 규칙 수로 정렬합니다.
- **중앙값과 사분위수를 씁니다.** 분개 금액은 소액이 많고 거액이 드문 한쪽으로 치우친 분포라서, 평균·표준편차는 이상치 자체에 끌려가 기준이 흔들립니다.
- **비교 대상이 적으면 판단하지 않습니다.** 최소 표본 수에 미달하는 계정·거래처는 규칙을 건너뛰고, 건너뛴 것을 화면에 적습니다 (미탐 가능성 안내).
- **모든 임계값은 기본값일 뿐**이며 사이드바에서 바꿀 수 있고, 다운로드 파일에 적용값이 함께 남습니다.
- 기준서 근거: 감사기준서 240은 분개 테스트 시 고려할 특성으로 관련 없거나 거의 쓰지 않는 계정, 평소 분개를 하지 않는 사람의 입력, 기말·결산 후 설명이 부족한 분개, 라운드 금액 등을 예시로 들고 있는 것으로 알고 있습니다. 해당 문단(적용지침)의 번호와 문구는 구현 전에 원문으로 확인하고 화면에 인용합니다.

### 규칙 요약

| 규칙 | 이름 | 단위 | 핵심 조건 (기본값) | MVP |
| --- | --- | --- | --- | --- |
| R1 | 계정별 금액 분포 이탈 | 분개 라인 | 같은 계정·같은 차대 방향 내 로그 금액이 Q3 + 3×IQR 초과 | 포함 |
| R2 | 과거 패턴 대비 이례적 금액·빈도 | 라인 / 계정-월 | 거래처별 중앙값의 5배 초과, 월별 건수·금액이 다른 달 중앙값의 3배 이상 또는 1/3 이하 | 포함 |
| R3 | 기말·결산 전후 및 비정상 시점 분개 | 전표 | 월말·결산일 전후 3영업일, 결산일 이후 입력, 주말 입력 | 포함 |
| R4 | 수기·조정 분개와 특정 조건 | 전표 | 수기·조정 유형, 입력자=승인자, 드문 입력자, 적요 없음·키워드 | 포함 |
| R5 | 신규 거래처·신규 조합 | 라인 | 파일 내 최초 등장이 마지막 2개월이고 거래처 합계가 기준금액 이상 | 포함 |
| R6 | 중복 가능 분개 | 라인 쌍 | 같은 계정·거래처·금액, 다른 전표, 7일 이내 | 포함 |
| R7 | 드문 계정과목 조합 | 전표 | 차변-대변 계정 쌍의 연간 출현 2회 이하 | 후순위 |
| R8 | 금액 기준 위험 신호 | 라인 | 라운드 금액, 승인 한도의 90\~100% 구간 | 후순위 |

### R1. 계정과목별 금액 분포 이탈

- **탐지 조건**: 같은 계정과목, 같은 방향(차변 또는 대변)의 라인들에서 금액에 로그를 취한 뒤, 사분위 범위(IQR)로 상한을 계산해 상한을 넘는 라인. 기본 배수 3, 계정별 최소 30건.
- **탐지 이유**: 같은 1억 원이라도 보험료 계정에서는 이례적이고 매출 계정에서는 평범합니다. 계정별로 비교해야 금액 자체가 아닌 "그 계정에서 드문 금액"을 찾습니다. 로그를 쓰는 이유는 치우친 분포에서 소액 거래가 많다는 이유만으로 보통 거래가 걸리지 않게 하기 위함입니다.
- **근거 표시**: 계정 중앙값, 상한, 실제 금액, 중앙값 대비 배수, 비교한 라인 수.
- **필요한 데이터**: account\_code, debit, credit.
- **한계와 오탐**: 연 1회 상여금·배당·자산 취득처럼 원래 크고 드문 거래가 걸립니다. 한 계정에 성격이 다른 거래가 섞이면 기준이 너무 넓어져 미탐이 생깁니다. 30건 미만 계정은 검사하지 않습니다.
- **테스트 방법**: 보통 거래 100건인 계정에 중앙값 20배 라인 1건을 넣어 걸리는지, 1.2배 라인은 걸리지 않는지, 10건짜리 계정은 건너뛰고 안내하는지 확인합니다.

### R2. 과거 거래 패턴 대비 이례적인 금액·빈도

- **탐지 조건**: (a) 거래처·계정 조합별로 이전 거래가 5건 이상일 때, 이번 금액이 이전 거래 중앙값의 5배를 넘는 라인. (b) 계정별 월간 건수·금액이 같은 계정 다른 달들의 중앙값 대비 3배 이상 또는 1/3 이하인 달.
- **탐지 이유**: R1이 "계정 전체에서 드문 금액"이라면, R2는 "이 거래처와 평소 하던 거래와 다름"을 봅니다. (b)는 특정 달에 비용·매출이 몰리거나 빠진 현상을 봅니다.
- **근거 표시**: 비교한 이전 거래 건수와 기간, 중앙값, 배수. (b)는 개별 라인이 아니라 기초 분석 화면의 계정-월 표에 표시합니다. 해당 월의 모든 라인을 후보로 올리면 후보가 지나치게 많아지기 때문입니다.
- **필요한 데이터**: vendor, account\_code, posting\_date, 금액.
- **한계와 오탐**: 업로드 파일이 1년치라면 "과거"는 같은 해의 앞선 달들입니다. 계절성(연말 매출 증가 등)을 구분하지 못하고, 전기 동월 비교는 전기 자료가 있어야 가능합니다. 거래처명 표기가 제각각이면("(주)가나" vs "가나주식회사") 다른 거래처로 봅니다.
- **테스트 방법**: 매달 비슷한 금액으로 거래하던 거래처에 10배 라인을 넣어 (a)가 걸리는지, 특정 월 건수를 4배로 부풀려 (b)가 걸리는지, 이전 거래 4건인 거래처는 건너뛰는지 확인합니다.

### R3. 기말·결산일 전후 및 비정상 시점 분개

- **탐지 조건**: (a) posting\_date가 월말 또는 결산일 전후 3영업일 이내. (b) entry\_date가 결산일 이후인데 posting\_date는 결산일 이전(결산 후 입력). (c) entry\_date가 토·일요일.
- **탐지 이유**: 기말과 결산 후 분개는 실적을 맞추려는 조정이 들어갈 수 있는 시점이고, 비영업일 입력은 평소 통제 흐름 밖일 수 있습니다.
- **근거 표시**: 결산일·월말까지의 영업일 수, 입력일과 회계처리일의 차이, 요일.
- **필요한 데이터**: posting\_date, entry\_date(없으면 (b)·(c)는 꺼짐), 결산일(사용자 입력).
- **한계와 오탐**: 기말에는 감가상각·충당금 같은 정상 결산 분개가 몰려 이 규칙 하나만으로는 후보가 많습니다. 그래서 결과 화면에서 다른 규칙과 함께 해당하는 건을 먼저 보게 합니다. MVP는 주말만 보고 공휴일은 반영하지 않습니다. 자동 배치 전표는 주말에도 정상적으로 생길 수 있습니다.
- **테스트 방법**: 결산일 12월 31일 기준 12월 29일·12월 20일, 입력일 1월 15일·회계처리일 12월 31일, 토요일 입력 등 경계값을 넣어 예상대로 걸리고 안 걸리는지 확인합니다.

### R4. 수기 분개 및 특정 조건의 조정 분개

- **탐지 조건**: (a) source가 수기 또는 je\_type이 조정·결산 등 사용자가 고른 값. (b) 입력자와 승인자가 같음. (c) 입력자의 연간 전표 수가 전체의 1% 미만(평소 분개를 거의 하지 않는 사람). (d) 적요가 비었거나 "수정", "조정", "오류", "임시" 같은 사용자 지정 키워드를 포함.
- **탐지 이유**: 자동 전표는 시스템 통제를 거치지만 수기·조정 분개는 사람의 판단이 개입하고, 직무 분리가 안 된 전표는 검토 필요성이 높습니다.
- **근거 표시**: 해당한 세부 조건, 입력자·승인자 이름, 입력자의 연간 전표 수, 일치한 키워드.
- **필요한 데이터**: source, je\_type, created\_by, approved\_by, description. 열이 없는 세부 조건은 꺼짐.
- **한계와 오탐**: "수기"를 나타내는 코드는 ERP마다 달라 사용자가 값을 골라야 합니다. 작은 회사는 입력자와 승인자가 같은 것이 일상일 수 있습니다. 키워드는 표현이 다양해 놓치는 것이 많습니다.
- **테스트 방법**: 세부 조건별로 해당하는 전표와 해당하지 않는 전표를 하나씩 만들고, 열이 없을 때 규칙이 오류 없이 꺼지는지 확인합니다.

### R5. 거래처 또는 거래 유형의 신규 출현

- **탐지 조건**: 파일 안에서 거래처의 최초 등장일이 분석 기간 마지막 2개월 안이고, 그 거래처의 기간 합계 금액이 사용자 지정 기준금액 이상. 같은 방식으로 기존 거래처의 처음 보는 계정 조합도 봅니다.
- **탐지 이유**: 기말에 갑자기 나타나 큰 금액을 거래한 거래처는 실재성·특수관계자 여부를 확인할 필요가 있을 수 있습니다.
- **근거 표시**: 최초 등장일, 거래 건수, 합계 금액, 기준금액.
- **필요한 데이터**: vendor, posting\_date, account\_code, 금액.
- **한계와 오탐**: "신규"는 업로드한 파일 기준일 뿐이며, 전기에 거래한 거래처도 신규로 보일 수 있습니다. 거래처 마스터가 없으므로 표기 차이가 오탐을 만듭니다. 기준금액은 감사인의 중요성 판단에 따라 달라져야 합니다.
- **테스트 방법**: 11월에 처음 나타난 거래처(기준금액 이상·미만), 3월부터 있던 거래처를 넣어 앞의 것만 걸리는지 확인합니다.

### R6. 동일하거나 유사한 분개의 중복 가능성

- **탐지 조건**: 서로 다른 전표번호인데 계정·거래처·금액이 같고 회계처리일 차이가 7일 이내인 라인 쌍. 적요가 있으면 적요 일치 여부도 함께 표시합니다.
- **탐지 이유**: 같은 증빙의 이중 입력은 비용·매출 과대계상이나 이중 지급으로 이어질 수 있습니다.
- **근거 표시**: 짝이 되는 전표번호, 두 날짜의 차이, 적요 일치 여부.
- **필요한 데이터**: je\_id, account\_code, vendor, 금액, posting\_date, description(선택).
- **한계와 오탐**: 같은 금액의 정상 반복 거래(주간 용역비 등)가 걸립니다. 금액을 조금 바꾼 중복이나 다른 거래처명으로 입력한 중복은 놓칩니다. 유사 적요 비교(문자열 유사도)는 후순위입니다.
- **테스트 방법**: 3일 간격 동일 라인 쌍(걸려야 함), 30일 간격 월 임차료(걸리면 안 됨), 같은 전표 안의 동일 금액 차대 라인(걸리면 안 됨)을 확인합니다.

### R7. 평소와 다른 계정과목 조합 (후순위)

- **탐지 조건**: 전표별 차변 계정과 대변 계정의 쌍을 만들고, 그 쌍이 연간 2회 이하로만 나타나는 전표.
- **탐지 이유**: "매출 / 대변 현금"처럼 평소 없는 조합은 비정상 회계처리의 단서가 될 수 있습니다.
- **필요한 데이터**: je\_id, account\_code, debit, credit.
- **한계와 오탐**: 차변·대변이 여러 줄인 복합 전표에서는 어느 차변이 어느 대변과 짝인지 알 수 없어 쌍이 과다하게 생깁니다. 드물지만 정상인 조합(자산 처분 등)이 많습니다. 이 두 가지 때문에 설명 방식을 더 다듬은 뒤 구현합니다.
- **테스트 방법**: 샘플에 "매출/현금" 조합 1건을 넣고, 복합 전표에서 쌍이 어떻게 만들어지는지 확인합니다.

### R8. 금액 기준 위험 신호 (후순위)

- **탐지 조건**: (a) 라운드 금액(예: 100만 원 단위로 나누어떨어지고 해당 계정에서 라운드 금액 비중이 낮은 경우). (b) 사용자가 입력한 전결 한도의 90\~100% 구간 금액이 같은 입력자에게 반복.
- **탐지 이유**: 추정치나 임의 조정은 라운드 금액이 되기 쉽고, 승인 한도 직하 금액의 반복은 분할 입력의 신호일 수 있습니다.
- **필요한 데이터**: 금액, account\_code, created\_by, 전결 한도(사용자 입력).
- **한계와 오탐**: 월 임차료·급여처럼 원래 라운드인 거래가 많습니다. 전결 한도는 회사 내부 규정이라 가상 데이터에서는 임의로 정해야 합니다.
- **테스트 방법**: 한도 1,000만 원 설정 시 990만 원 입력이 반복되는 사례와 월 임차료를 넣어 각각 확인합니다.

### 검토했지만 제외한 방법

- **벤포드 법칙(첫자리 숫자 분포)**: 모집단 전체의 분포 이상을 보여줄 뿐 개별 거래를 지목하지 못하고, 가상 데이터에서는 결과가 데이터 생성 방식에 좌우됩니다. 기초 분석 화면의 참고 그래프로만 후순위 검토합니다.
- **머신러닝 이상치 탐지**: 왜 걸렸는지 한 문장으로 설명하기 어렵고 가상 데이터로는 성능을 검증할 수 없어 "모든 결과에 근거 표시" 원칙과 맞지 않습니다.

## 7. 테스트 전략

핵심은 **정답을 아는 가상 데이터**입니다. 샘플 생성기가 "어느 전표에 어떤 이상을 심었는지" 정답표를 함께 만들고, 탐지 결과를 정답표와 대조합니다.

| 수준 | 무엇을 | 어떻게 | 통과 기준 |
| --- | --- | --- | --- |
| 단위 테스트 | 규칙 하나, 검증 항목 하나 | 5\~20행짜리 작은 표를 직접 만들어 pytest로 자동 실행 (6절의 규칙별 테스트 방법) | 걸려야 할 행은 걸리고, 안 걸려야 할 행은 안 걸림 |
| 경계값 테스트 | 임계값 바로 위·아래 | 상한 정확히 같은 값, 1원 많은 값 등 | 설계서의 "초과 / 이상" 정의대로 동작 |
| 입력 오류 테스트 | 깨진 파일 | 필수 열 누락, 글자 섭인 금액, 빈 파일, CP949 CSV, 차대 불일치 | 프로그램이 멈추지 않고 오류·경고 메시지를 냄 |
| 통합 테스트 | 샘플 1년치 전체 | 생성 → 검증 → 탐지 → 다운로드를 한 번에 실행 | 심어 둔 이상 건의 탐지율, 정상 건 중 후보 비율(오탐률)을 숫자로 기록 |
| 화면 테스트 | 사용 흐름 | 점검표를 따라 직접 클릭 (자동화는 후순위) | 점검표 항목별 통과·실패 기록 |
| 성능 확인 | 큰 파일 | 10만·20만 행 가상 파일 | 분석 시간을 측정해 기록 (목표는 4단계에서 정함) |

통합 테스트의 탐지율은 "우리가 심은 유형을 규칙이 제대로 찾는가"만 보여주며, 실제 데이터에서의 탐지 성능을 뜻하지 않습니다. 포트폴리오 문서에도 이 구분을 그대로 씁니다. 테스트 결과는 실제 실행한 출력과 함께만 "통과"로 기록합니다.

## 8. 예상되는 개발상 위험 및 해결 방법

가장 큰 위험은 기술보다 **후보가 너무 많아 쓸모없어 보이는 것**과 **가상 데이터에서만 잘 되는 것**입니다.

| 위험 | 영향 | 해결 방법 |
| --- | --- | --- |
| 검토 후보 과다 (기말 분개만 수천 건) | 감사인이 결과를 신뢰하지 않음 | 규칙별 건수 요약, 해당 규칙 수 정렬, "2개 이상 규칙 해당" 필터, 통합 테스트에서 오탐률 측정 후 기본값 조정 |
| 가상 데이터가 너무 단순해 규칙이 항상 성공 | 포트폴리오 설득력 저하 | 정상인데 드문 거래(상여금, 자산 취득)와 계절성을 일부러 넣어 오탐도 나오게 구성 |
| 실제 ERP 파일 형식이 제각각 | 업로드 실패 | 열 매핑 화면, 차대 두 열 표준, 한글 인코딩 자동 시도, 지원 형식을 안내 화면에 명시 |
| 파일이 커서 느림 | 화면이 멈춘 것처럼 보임 | Streamlit 캐시로 재계산 방지, pandas 묶음 연산 사용(행별 반복문 금지), 20만 행 초과 시 경고 |
| 코드가 커져 이해·수정이 어려움 | 초보자가 유지보수 불가 | 규칙 하나당 파일 하나, 같은 모양의 함수(입력: 표와 기준값, 출력: 해당 여부와 사유), 한글 주석 |
| 감사기준 인용 오류 | 전문성 신뢰 훼손 | 인용은 원문 확인 후에만 화면에 넣고, 확인 못 한 부분은 "확인 필요"로 표시 |
| 탐지를 결론처럼 읽는 오해 | 탐지 도구의 오용 | "부정·위험 점수" 표현 사용 안 함, 모든 다운로드 파일 첫 시트에 한계 안내 |
| 실제 자료 유출 | 기밀 유출 | 업로드 파일 저장 안 함, 웹 배포 시 실제 자료 업로드 금지 안내, 저장소에는 가상 데이터만 |
| 단계를 건너뛴 일괄 개발 | 작동하지 않는 큰 코드 덩어리 | MVP도 "업로드·검증 → 기초 분석 → 규칙 1개씩" 작은 단위로 나눠 매번 실행 확인 |

## 9. 포트폴리오에서 보여줄 수 있는 핵심 역량

AuditLens가 보여줄 수 있는 것은 "코딩을 할 줄 안다"보다 **감사 판단을 데이터 규칙으로 바꾸고 그 한계를 설명하는 능력**입니다.

| 역량 | 보여주는 산출물 |
| --- | --- |
| 감사 전문성: 분개 테스트 위험 요소를 이해하고 규칙으로 정의 | 6절의 규칙 설계서, 화면의 규칙 설명 페이지 |
| 전문가적 회의주의: 탐지와 결론의 구분, 오탐·미탐 인식 | 한계 안내 화면, 규칙별 한계, 제외한 방법과 이유 |
| 데이터 분석: 치우친 분포에 맞는 통계 선택, 비교 기준 설정 | R1·R2의 중앙값·사분위수 설계와 그 이유 |
| 데이터 품질 관리 | 검증 항목 V1\~V11과 검증 결과 화면 |
| 검증하는 습관 | 정답표 기반 테스트 결과(탐지율·오탐률), pytest 자동 테스트 |
| 실행 가능한 도구 제작 | 샘플 데이터로 바로 돌아가는 앱, GitHub 저장소, 시연 영상 |
| AI 활용 능력 | AI와 단계별로 협업한 과정(요구사항 → 설계 → 구현 → 검증) 기록과 직접 내린 판단 |

6단계에서는 README(문제·해결·실행 방법·한계), 규칙 설계서, 테스트 결과 보고서, 화면 캐픈처와 2\~3분 시연 영상을 만드는 것을 제안합니다.
